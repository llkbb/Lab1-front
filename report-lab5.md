## 1. Мета лабораторної роботи

Вивчити основні прийоми створення гнучкого й адаптивного дизайну, способи забезпечення кросбраузерності та методи вимірювання ефективності фронтенду програмних систем.

## 2. Постановка завдання

1. Вивчити прийоми реалізації гнучкого та адаптивного дизайну, кросбраузерності й інструменти вимірювання ефективності фронтенду.
2. Перевірити адаптивність фронтенду, реалізованого в лабораторних роботах 1–4, на стандартних розмірах екранів. Перевірити навігацію, меню, каталог курсів і форму зворотного зв'язку. За необхідності внести зміни до коду та сформувати таблицю результатів.
3. Перевірити кросбраузерність використаних HTML-тегів і CSS-властивостей для Chrome, Edge/Internet Explorer, Firefox, Safari та Opera. Сформувати таблицю відповідності.
4. Провести заміри основних метрик ефективності програмного продукту та оформити таблиці результатів. Проаналізувати можливі причини низьких показників.

## 4. Виконані покращення

### 4.1. Адаптивність

Для перевірки та покращення адаптивності:

- збережено viewport-метатег на всіх сторінках;
- використано відносні одиниці `rem`, `%`, `vw`, `clamp()`;
- додано медіа-запити для ширини до `850 px`, `700 px`, `560 px` і `420 px`;
- навігація на вузьких екранах переходить у кілька рядків і не виходить за межі viewport;
- сітка hero-блоку, карток курсів і footer стає одноколонковою;
- форма зворотного зв'язку переходить на одноколонковий вигляд;
- зображення отримали `max-width: 100%`, атрибути `width` і `height`;
- додано `overflow-x: hidden` для запобігання горизонтальному прокручуванню сторінки;
- додано окремі правила для дуже вузьких екранів `320–420 px`.

### 4.2. Оптимізація завантаження

Для зменшення початкового навантаження:

- зображення, які не належать до першого екрану, мають `loading="lazy"`;
- для відкладених зображень додано `decoding="async"`;
- для зображень задано реальні атрибути `width` і `height`, що зменшує layout shift;
- головне hero-зображення має `fetchpriority="high"`;
- для анімацій додано підтримку `prefers-reduced-motion`.

## 5. Перевірка адаптивності

Перевірка виконувалась у браузері через Responsive Design Mode на ширинах `320 px`, `768 px` і `1440 px`.

| Сторінка | 320 px | 768 px | 1440 px | Горизонтальний overflow |
|---|---:|---:|---:|---|
| Головна | пройдено | пройдено | пройдено | відсутній |
| Курси | пройдено | пройдено | пройдено | відсутній |
| Зворотний зв'язок | пройдено | пройдено | пройдено | відсутній |

Додатково перевірено:

| Елемент | Результат |
|---|---|
| Навігаційне меню | Не виходить за межі viewport, доступне на всіх ширинах |
| Каталог курсів | Картки переходять у вертикальний список |
| Таблиця навчальних тем | Зберігає горизонтальну прокрутку всередині контейнера |
| Форма | Поля переходять у вертикальний порядок на малих екранах |
| Flip-картка | Зменшується до ширини контейнера |
| Tooltip | Переміщується під полем на вузькому екрані |

**Місце для скріншотів Responsive Design Mode:**

> Вставити скріншоти головної сторінки, каталогу та форми на ширинах 320 px і 768 px.

Для застарілих браузерів базова HTML-структура та форма залишаються доступними, але сучасні візуальні ефекти можуть бути недоступними.

## 7. Вимірювання ефективності

Під час локального запуску через браузер було виміряно час завершення DOMContentLoaded і load event за допомогою Navigation Timing API.

| Сторінка | DOMContentLoaded, ms | Load event, ms | Зображень | Lazy-зображень |
|---|---:|---:|---:|---:|
| Головна | 69 | 70 | 2 | 1 |
| Курси | 60 | 61 | 4 | 4 |
| Зворотний зв'язок | 51 | 59 | 0 | 0 |

Ці значення отримані в локальному браузерному запуску, тому вони не замінюють повний Lighthouse/PageSpeed тест у мережевому середовищі. Вони використовуються для порівняння структури сторінок між собою.

| Метрика або фактор | Стан після покращень |
|---|---|
| Горизонтальний overflow | Відсутній на 320, 768 і 1440 px |
| Резервування місця під зображення | Виконано через `width` і `height` |
| Відкладене завантаження | 5 із 6 контентних зображень мають `loading="lazy"` |
| Асинхронне декодування | Додано до відкладених зображень |
| Оптимізація анімацій | Додано `prefers-reduced-motion` |
| Адаптивні брейкпоінти | 850, 700, 560 і 420 px |
| Семантична структура | Використано HTML5-елементи та ARIA-атрибути |

Можливі причини нижчих показників у повному Lighthouse:

- зовнішні зображення Unsplash залежать від мережі;
- зовнішній Google Fonts stylesheet створює додатковий запит;
- анімований hero-блок використовує compositing і CSS transforms;
- великі зображення можуть мати більший фактичний розмір, ніж потрібно для конкретного viewport;
- запуск із `file://` не відтворює повністю умови production-сервера.

**Місце для скріншотів Lighthouse/PageSpeed:**

> Вставити скріншоти вкладок Performance, Accessibility і Best Practices.

## 9. Висновки

Під час виконання лабораторної роботи було перевірено адаптивність вебпорталу на малих, середніх і великих ширинах екрана. Було усунуто горизонтальне переповнення сторінок, додано додаткові брейкпоінти та покращено поведінку навігації, каталогу й форми. Для зображень реалізовано гнучку ширину, резервування розміру, lazy-loading і асинхронне декодування. Було проаналізовано підтримку використаних HTML5, CSS і JavaScript-технологій у сучасних браузерах та Internet Explorer. За допомогою Navigation Timing API отримано базові значення часу завантаження сторінок. Також визначено чинники, які можуть погіршувати показники Lighthouse, зокрема зовнішні зображення, шрифти та анімації.
